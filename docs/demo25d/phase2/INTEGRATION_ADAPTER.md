# Future integration adapter — connecting approved sprite animations to the current character controller

**Documentation only. Not implemented. No Godot run, no gameplay change.** Build it only after the assets pass `tools/validate_approved_art.py`, the manual checklist and owner approval.

## What exists today (prototype controller, `scripts/demo/`)
- `SpriteActor` (`sprite_actor.gd`): node with `char_id`, `wx` (world x), `z` (depth 0..1), `dir` ("down","up","left","right"), `moving`, `radius` (footprint), signal `footstep`; `setup(id)`, `set_dir(d)`, `animate(delta, is_moving, rate)`, `face_toward(px,pz)`, `set_tint`. It loads **one strip per view** (`front/back/side`, 5 frames, 144x288) from `assets/demo25d/chars/` into a `Sprite2D` (`hframes=5`), flips `side` for left, adds a soft shadow sprite and a flipped reflection sprite. Walk cycle: frame = 1 + int(anim_t) % 4 at 8 fps x rate; `footstep` fires on frames 2 and 4. `BASE_SCALE` multiplies the depth scale. Portraits come from `portrait()` / `portrait_mip()` and the `DialogueBox` `tex:` speaker option.
- `Stage25` (`stage25.gd`): places actors at `(wx, 392 + z*264)` with scale `s_of(z) * BASE_SCALE` (0.74..1.0), y-sorts them, runs collisions using `radius`, drives the player (`tick`) and NPC/pedestrian AI, and sets facing from movement (dominant axis, 1.35 bias).

## Adapter requirements (new files; prototype stays as fallback)
1. **New actor class** (e.g. `ApprovedActor`, same public surface as `SpriteActor`: `setup`, `set_dir`, `animate`, `face_toward`, `footstep`, `wx`, `z`, `dir`, `radius`) so `Stage25` and the NPC AI need no logic changes. Selected by a feature flag / separate `visual_checkpoint` scene; existing episodes, missions, saves, combat and progression untouched.
2. **Asset loading:** build one `SpriteFrames` per character with `tools/build_spriteframes.gd` from `assets/approved_anime/characters/<id>/manifest.json`. Animations `front_idle, front_walk, right_idle, right_walk, back_idle, back_walk, left_idle, left_walk`; idle 2 frames @4 fps loop, walk 6 frames @9 fps loop. Use an `AnimatedSprite2D` (or `Sprite2D` + frame index); **no `flip_h`** — left uses its own frames.
3. **Direction mapping:** `down -> front`, `up -> back`, `right -> right`, `left -> left` (replaces the current `side`+flip mapping).
4. **Anchor and scale:** master frames are 576x1152 with the ground-contact point at (288, 1088) (`anchor.json`). Set `centered=false`, `offset=(-288,-1088)` so the node origin is the ground point (matches `SpriteActor`'s "origin = ground between the feet"). Display scale = `s_of(z) * 0.25` for the 576x1152 masters (or `s_of(z) * 0.5` if a 2:1 runtime package at 288x576 is used), which puts the 1000 px hero figure at ~250 px tall at z=1 and ~185 px at z=0 in the 1280x720 view. These replace the prototype's `BASE_SCALE`, `offset=(0,-132)` and `FRAME_W/H = 144/288` for this class only. The target size is confirmed visually at the checkpoint review; if it needs changing, change one global constant, never redraw.
5. **Walk-cycle driving:** replace the 4-frame cycle with the 6-frame loop: frame = int(anim_t) % 6 at ~9 fps x speed rate (clamped 0.6-1.1 as now); idle frames alternate at 4 fps. `footstep` fires on the two foot-contact frames (walk_00 and walk_03 — confirm against the delivered cycle). Switching direction restarts the loop on the matching phase to avoid pops; optional turn transitions are played if supplied.
6. **Shadow/reflection:** keep the shared soft shadow and a flipped, squashed, tinted reflection built from the same `SpriteFrames` (no separate art).
7. **Footprint and collisions:** keep `radius` in world px (e.g. (15, 6)) independent of art size; the art never changes collision.
8. **Rigged characters:** the rig is exported offline to the frame contract, so the engine needs no skeleton code. A runtime `Skeleton2D` path is optional and out of scope for the checkpoint.
9. **Portraits:** `assets/approved_anime/characters/<id>/portrait.png` and `portrait_<expression>.png` (1024x1024, transparent) loaded through a new lookup and passed to `DialogueBox` via the existing `tex:` portrait path with mipmaps; expression chosen per dialogue line (later).
10. **Environment:** a new `NeonDistrictLayers` builder (not the procedural `NeonArt`) loads `sky.png`, `far_skyline.png`, `mid_buildings_0..2`, `street_floor_0..2`, `foreground_0..3`, props, occluders and light masks at the origins/parallax in `PRODUCTION_ASSET_MANIFEST.md` section 5 (sprite scale 0.5), reusing `Stage25`'s camera, parallax and occlusion fade. Static layers are plain textures (no per-frame bake); chunk textures stay <= 3200 px wide.
11. **Memory/perf check (when built):** report texture memory (a 576x1152 master frame is ~2.6 MB uncompressed (32 frames = ~85 MB per character) while the 288x576 runtime package is ~0.66 MB (~21 MB)); decide compression (ETC2/ASTC), atlasing or loading only the active characters; measure on real devices, not software GL.
12. **Test plan (when built):** reuse the existing demo tests (movement in four directions, collisions, depth sort, occlusion, camera, dialogue, mobile controls) plus anchor/scale assertions, the four-view animation names, and screenshots at 1280x720, 844x390 and 667x375. Report real results only.
